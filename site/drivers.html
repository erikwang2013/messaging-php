P1 / Driver

ActiveMQ Classic 驱动

驱动名：activemq · 命名空间：Erikwang2013\Messaging\Driver\Stomp · 协议：STOMP 1.2 over TCP。

与 Artemis 共用 StompDriver，差异只在 ActiveMqPreset 的端口、requeue 与延迟头。

配置

键 类型 默认 说明
host string 必填 broker 地址
port int 61613 STOMP 连接器端口
login string|null admin CONNECT 登录名；null 时不发送
passcode string|null admin CONNECT 密码；null 时不发送
prefix string /queue/ 目标名前缀；目标名已以 /queue/ 或 /topic/ 开头时原样使用
timeout float 5.0 TCP 连接与 CONNECTED 握手超时（秒）；消费超时由 ReceiveOptions::timeoutMs 控制
buffer_limit int 10000 单个非当前目标的未读消息缓冲上限（条）；超出时断开连接并抛 ConnectionException
PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Driver\Stomp\ActiveMqFactory;
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'mq',
    'connections' => [
        'mq' => ['driver' => 'activemq', 'host' => '127.0.0.1', 'port' => 61613,
                 'login' => 'admin', 'passcode' => 'admin'],
    ],
]);
$manager->extend('activemq', new ActiveMqFactory());

$connection = $manager->connection();
$connection->publish('orders', new Message('payload', ['trace' => 'abc'], 'order-1'));

$message = $connection->receive('orders', new ReceiveOptions(5000));
$message?->ack();

能力

能力 支持 说明
ack ✓ ACK（订阅使用 ack:client-individual）
requeue ✓ reject(true) 重新发布原消息后确认原投递；reject(false) 等同 ACK 丢弃
delay ✓ AMQ_SCHEDULED_DELAY（相对毫秒）；broker 必须开启 schedulerSupport="true"
consumer groups ✗ 同一队列的多个消费者自然竞争；协议无 group 概念
batch publish ✗ 抛 UnsupportedFeatureException
ordering ✗ 不保证 FIFO
headers ✓ 标量 header；int/float/bool 经 x-messaging-types 保留类型
requiresActiveSubscription ✗ broker 在首次 SEND 时自动建队列

requeue 为什么不是 NACK

ActiveMQ Classic 把 STOMP NACK 当作 poison ACK：STOMP SEND 默认发布非持久消息，默认 DLQ 策略会直接丢弃它们；持久消息则进入 ActiveMQ.DLQ。两种情况都不会回到原队列，且非持久消息是静默丢失。

因此 reject(true) 的实现是：按原 body、目标、自定义 header、correlation-id、persistent、priority 和 x-messaging-id 重新 SEND，成功后再 ACK 原投递。重投后的 ReceivedMessage::attempts() 递增（通过内部头 x-messaging-attempts 传递）。两步之间断线会重复投递（at-least-once），不会丢消息。需要 broker 侧 DLQ 语义时，请在发布时显式设置 'persistent' => true。

协议范围

  • STOMP 1.2 帧：COMMAND\nheader:value\n\n<body>\0；header 按规范转义（\\、\n、\r、\c、:），CONNECT/STOMP/CONNECTED 帧不转义。接受 CRLF。
  • 非空 body 自动写 content-length，二进制 body（含 NUL）安全往返。
  • 握手：STOMP + accept-version:1.2、host、login/passcode、heart-beat:0,0（关闭心跳）。CONNECT ERROR 抛 AuthenticationException；版本协商失败抛 ProtocolException。
  • 发布：SEND + destination + 自定义 header；Message::key 写入 correlation-id。PublishResult::id 是客户端生成的 32 位十六进制 id，同时写入 x-messaging-id；broker 不提供同步发布回执。
  • 消费：每个目标保持一个持久 SUBSCRIBE（id: sub-N、ack:client-individual）；一次 receive() 只返回该目标的消息，其它目标的 MESSAGE 帧按目标缓冲复用。
  • 跨目标缓冲上限：单个非当前目标的未读消息达到 buffer_limit（默认 10000）时，驱动断开连接并抛 ConnectionException；未确认消息由 broker 重投。上限按目标分别计数，不同目标的数量本身不设上限。
  • 超时：timeoutMs = 0 永久阻塞；> 0 到期返回 null。读到半个帧后超时视为连接失步，抛 ConnectionException 并丢弃连接。
  • ack() 发送 ACK id:<MESSAGE 的 ack/message-id>；reject(false) 也发 ACK。ACK 闭包绑定连接代次，重连后旧消息再确认会抛 ConnectionException（broker 会重投未确认消息）。
  • ERROR 帧在 receive() 时抛 ProtocolException 并断开；下次调用重新连接并重新订阅已跟踪的目标。close() 尽力发送 DISCONNECT。
  • header 值仅支持标量；数组/对象抛 UnsupportedFeatureException。destination、content-length、x-messaging-id、x-messaging-types、x-messaging-attempts 为保留名。
  • 未实现：事务、receipt、TLS、consumer group、批量发布。

ActiveMQ Artemis 驱动

驱动名：artemis · 命名空间：Erikwang2013\Messaging\Driver\Stomp · 协议：STOMP 1.2 over TCP。

与 ActiveMQ Classic 共用 StompDriver，差异在 ArtemisPreset：NACK 语义、延迟头与队列创建时机。

配置

键 类型 默认 说明
host string 必填 broker 地址
port int 61613 STOMP acceptor 端口；docker-compose 将容器 61613 映射到宿主机 61614
login string|null admin CONNECT 登录名；apache/artemis 镜像默认是 artemis
passcode string|null admin CONNECT 密码；apache/artemis 镜像默认是 artemis
prefix string /queue/ 目标名前缀；目标名已以 /queue/ 或 /topic/ 开头时原样使用
timeout float 5.0 TCP 连接与 CONNECTED 握手超时（秒）；消费超时由 ReceiveOptions::timeoutMs 控制
buffer_limit int 10000 单个非当前目标的未读消息缓冲上限（条）；超出时断开连接并抛 ConnectionException
PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Driver\Stomp\ArtemisFactory;
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'mq',
    'connections' => [
        'mq' => ['driver' => 'artemis', 'host' => '127.0.0.1', 'port' => 61614,
                 'login' => 'artemis', 'passcode' => 'artemis'],
    ],
]);
$manager->extend('artemis', new ArtemisFactory());

$connection = $manager->connection();
// Artemis 在消费者首次 attach 时创建队列；先订阅，避免发布被丢弃。
$connection->receive('orders', new ReceiveOptions(1));
$connection->publish('orders', new Message('payload'));

$message = $connection->receive('orders', new ReceiveOptions(5000));
$message?->ack();

NACK / 重投限制

Artemis 的 STOMP NACK 与 ACK 等效，消息直接丢弃（ARTEMIS-1983）。驱动因此声明 requeue = false：

  • reject(false) 发送 ACK，丢弃消息。
  • reject(true) 在发送任何帧之前抛 UnsupportedFeatureException，提示通过关闭消费者连接触发重投。
  • 连接断开时，未确认消息会由 broker 重新投递；驱动重连后清空本地缓冲并重新订阅，旧投递的 ack 闭包会抛 ConnectionException。

队列创建时机

Artemis 按地址/队列模型工作：SEND 会创建地址，但队列在第一个消费者 attach 时才创建；没有队列时消息被丢弃。因此 requiresActiveSubscription = true，共享契约测试会先订阅再发布。生产环境建议预创建队列，或先调用一次 receive() 建立订阅。

协议范围

  • STOMP 1.2 帧：COMMAND\nheader:value\n\n<body>\0；header 按规范转义（\\、\n、\r、\c、:），CONNECT/STOMP/CONNECTED 帧不转义。接受 CRLF。
  • 非空 body 自动写 content-length，二进制 body（含 NUL）安全往返。
  • 握手：STOMP + accept-version:1.2、host、login/passcode、heart-beat:0,0（关闭心跳）。CONNECT ERROR 抛 AuthenticationException；版本协商失败抛 ProtocolException。
  • 发布：SEND + destination + 自定义 header；Message::key 写入 correlation-id。PublishResult::id 是客户端生成的 32 位十六进制 id，同时写入 x-messaging-id。
  • 延迟：Message::delayMs > 0 时写 AMQ_SCHEDULED_DELAY（相对毫秒）。
  • 消费：每个目标保持一个持久 SUBSCRIBE（id: sub-N、ack:client-individual）；一次 receive() 只返回该目标的消息，其它目标的 MESSAGE 帧按目标缓冲复用。

Beanstalkd 驱动

纯 PHP 实现的 Beanstalkd 文本协议客户端。目标（destination）即 tube 名。

配置

键 类型 默认 说明
host string 必填 服务器地址
port int 11300 端口
priority int 1024 put 使用的优先级（0 最高）
ttr int 60 time-to-run，秒
timeout float 5.0 TCP 连接超时与普通读写超时，秒
PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Driver\Beanstalkd\BeanstalkdFactory;
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'queue',
    'connections' => [
        'queue' => ['driver' => 'beanstalkd', 'host' => '127.0.0.1', 'port' => 11300],
    ],
]);
$manager->extend('beanstalkd', new BeanstalkdFactory());

$connection = $manager->connection();
$connection->publish('orders', new Message('payload'));

$message = $connection->receive('orders', new ReceiveOptions(5000));
$message?->ack();

能力

能力 支持 说明
ack ✓ delete
requeue ✓ reject(true) 用 release 保留原优先级、延迟 0；reject(false) 等同 delete
delay ✓ Message::delayMs 向上取整为秒
consumer groups ✗ 同一 tube 竞争消费
batch publish ✗ 抛 UnsupportedFeatureException
ordering ✗ 按优先级/延迟调度，不保证 FIFO
headers ✗ 非空 headers 抛 UnsupportedFeatureException

key 同样不支持：设置后 publish 抛 UnsupportedFeatureException，不会被静默丢弃。

协议范围

命令：use、watch、ignore、put、reserve-with-timeout、delete、release、stats-job。协议本身不提供 TLS 与认证。

  • body 按原始字节写入，长度前缀取自 strlen，二进制安全。
  • 接收超时协议只支持整秒：timeoutMs = 0 发送 reserve-with-timeout 0（永久阻塞）；timeoutMs > 0 发送 max(1, ceil(ms / 1000))，因此 10ms 实际等待约 1 秒。TIMED_OUT 与 DEADLINE_SOON 都返回 null。
  • reject(true) 先 stats-job <id> 读取原始优先级再 release；拿不到时回退到连接配置的 priority。
  • attempts() 固定为 1，不额外请求 stats-job。
  • tube 名在发送前按 Beanstalkd 规则校验（1–200 字节的字母、数字与 -+/;.$_()），避免命令注入。
  • 连接惰性建立；close() 后再操作会重新连接。

错误映射

情况 异常
TCP 连接/读写失败 ConnectionException
套接字读超时 TimeoutException
响应无法解析（空行、缺字段、body 无 CRLF 结尾、未知状态） ProtocolException
broker 拒绝请求（NOT_FOUND、JOB_TOO_BIG、DRAINING、BURIED 等） RequestException

限制

  • 不支持 headers、key、批量发布，能力声明与行为一致。
  • 不做自动重连与连接池；每个连接同一时刻只应被一个进程使用。
  • Beanstalkd 在内存不足时对 put 返回 BURIED <id>，本驱动按请求失败抛 RequestException（不静默接受）。

NATS 驱动

驱动名：nats · 命名空间：Erikwang2013\Messaging\Driver\Nats · 实现：NatsDriver / NatsFactory

当前实现范围：NATS Core 文本协议。JetStream（持久化、ack、重投、延迟、消费者组持久订阅）不在本阶段范围内，见文末。

配置

键 必填 默认 说明
host 是 — 服务器地址
port 否 4222 服务器端口（整数或数字字符串）
user 否 null CONNECT 用户名；设置 pass 时必须同时设置 user
pass 否 null CONNECT 密码
queue_group 否 null 订阅使用的 queue group；非空时 consumerGroups 能力为 true
timeout 否 5.0 连接、握手与帧读取超时（秒）
headers 否 true 是否启用 headers；服务器不支持时自动降为 false
buffer_limit 否 10000 每个 destination 的待取消息缓冲上限（正整数）；超限抛 ProtocolException

TLS 暂未开放配置（tls_required 固定为 false），TLS 端点留待后续版本。

PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Manager;

$mq = new Manager([
    'default' => 'nats',
    'connections' => [
        'nats' => [
            'driver' => 'nats',
            'host' => '127.0.0.1',
            'port' => 4222,
            'queue_group' => 'workers', // 可选
        ],
    ],
]);
$connection = $mq->connection();

// Core NATS 只向已存在的订阅投递：先建立订阅，再发布。
$connection->receive('orders.created', new ReceiveOptions(1));

$connection->publish('orders.created', new Message('hello'));
$message = $connection->receive('orders.created', new ReceiveOptions(1000));

能力

能力 值 说明
ack false Core NATS 至多一次，投递即消费；ack() 抛 UnsupportedFeatureException
requeue false 不支持；reject() 抛 UnsupportedFeatureException
delay false 不支持延迟投递；Message::$delayMs 非空时抛 UnsupportedFeatureException
consumerGroups 配置 queue_group 时 true 通过 SUB <subject> <queue> <sid> 实现
batchPublish false publishBatch() 抛 UnsupportedFeatureException
ordering true 单连接内按发布顺序投递
headers 默认 true 需服务器 INFO 声明 headers:true，否则自动降为 false；header 值为字符串
requiresActiveSubscription true 只向发布前已建立的订阅投递

协议范围

  • 握手：读取 INFO {json}，发送 CONNECT {...}（含 headers:true）与 PING，等待 PONG。
  • 发布：无 headers 时 PUB <subject> [reply] <bytes>\r\n<body>\r\n；有 headers 时 HPUB <subject> [reply] <header-bytes> <total-bytes>\r\nNATS/1.0\r\n...\r\n\r\n<body>\r\n。 每次发布后以 PING/PONG 冲刷，确保已写入服务器。发布/冲刷遇到 ConnectionException 或 TimeoutException（如连接被服务器的 ping 窗口关闭）时，驱动关闭旧 socket、重新握手， 并把同一帧重发一次；Core NATS 至多一次，重发可能产生重复投递。
  • 订阅：收到 MSG/HMSG 后缓冲，由 receive() 取出；第一次 receive() 某个 destination 时才发送 SUB <subject> [queue] <sid>，因此发布前必须先订阅。receive() 的 timeoutMs 为 0 时一直阻塞，超时返回 null。
  • 控制帧：响应服务器心跳 PING（回 PONG），忽略 +OK/INFO，-ERR 映射为 ProtocolException，认证类错误映射为 AuthenticationException。
  • 连接失败抛 ConnectionException，读取超时抛 TimeoutException（receive() 自身的 超时除外），畸形帧抛 ProtocolException。
  • body 二进制安全，支持零长度消息。

语义与限制

  • 至多一次：订阅采用 Core NATS 的即时投递，没有持久化；消费者离线期间的消息会丢失。
  • ReceivedMessage::ack() 与 reject() 都抛 UnsupportedFeatureException（能力为 ack:false / requeue:false），驱动不会静默忽略确认请求。
  • Core NATS 没有消息 id / key 概念：驱动在发布时生成 id，并把 id 与 key 编码进 Messaging-Id / Messaging-Key 头，接收时还原并从 headers() 中移除。因此这两个 字段要求服务器与连接双方都支持 headers；服务器不支持 headers 时 publish() 返回的 id 为 null。
  • header 值在 NATS 线上只能是字符串：发布时数字、布尔值、浮点数会转成字符串，接收时 一律按字符串返回（['attempt' => 2] 会变成 ['attempt' => '2']），驱动不会猜测类型。
  • 必须先订阅再发布（requiresActiveSubscription: true）：publish() 不会隐式创建 订阅。同一连接想取回自己发布的消息，也要先调用一次 receive()（即使是 1ms 超时）建立 订阅；跨连接消费同理，订阅方必须先启动。
  • 缓冲上限：每个 destination 最多缓存 buffer_limit（默认 10000）条尚未被 receive() 取走的消息；接收 A 时到达的 B 消息、以及发布冲刷期间到达的消息都会占用 该额度。超过上限抛 ProtocolException，避免慢消费者无限占用内存。该异常不会被发布重试 逻辑当作断线处理。
  • 空闲重连：服务器关闭空闲连接（ping 窗口）后，下一次 publish() 会自动重连并重发 一次；重连后旧订阅失效（订阅是连接级的），需要重新 receive() 建立。
  • 每次 publish() 都做一次 PING/PONG 往返，吞吐低于批量客户端；这是可靠交付边界的取舍。
  • 未配置 queue_group 时每个连接都是独立订阅者，消息会广播给所有订阅者。

JetStream（后续阶段）

JetStream 需要额外的 API（$JS.API.> 请求、stream/consumer 创建、pull 订阅、 ack/NAK/term、延迟与重投）。本驱动不包含这些能力，也不会静默降级：需要持久化或确认 语义时请使用 JetStream 客户端或等待后续版本。

NSQ 驱动

纯 PHP 实现的 NSQ v2 TCP 协议客户端（Erikwang2013\Messaging\Driver\Nsq），不依赖 nsq 官方 SDK。

配置

PHP
use Erikwang2013\Messaging\Manager;
use Erikwang2013\Messaging\Driver\Nsq\NsqFactory;

$manager = new Manager([
    'default' => 'nsq',
    'connections' => [
        'nsq' => [
            'driver' => 'nsq',
            'host' => '127.0.0.1',   // 必填
            'port' => 4150,          // 默认 4150
            'channel' => 'default',  // 默认 default，同一 topic 的多个消费者可共用该 channel 竞争消费
            'timeout' => 5.0,        // 连接与握手读超时（秒），默认 5.0
            'requeue_delay_ms' => 0, // reject(true) 的 REQ 延迟，默认 0
        ],
    ],
]);
$manager->extend('nsq', new NsqFactory());

$conn = $manager->connection('nsq');

destination 即 NSQ topic。一个驱动实例复用一个发布连接，并为每个消费 topic 各保持一个消费连接（NSQ 单连接只允许一次 SUB）。

能力

能力 支持 说明
ack ✓ FIN <id>
requeue ✓ REQ <id> <delay>；reject(false) 等同 FIN（丢弃）
delay（发布） ✗ 发布带 delayMs 抛 UnsupportedFeatureException
consumer group ✗ NSQ channel 本身即竞争消费语义，但驱动不暴露 group 管理
batch publish ✗ 抛 UnsupportedFeatureException
ordering ✗ 不保证顺序
headers ✗ 非空 headers 或 key 抛 UnsupportedFeatureException，不会静默丢弃

ReceivedMessage::attempts() 来自消息帧里的 attempts 字段；第一次投递为 1。

协议范围

  • 连接：发送 4 字节 magic V2
  • 发布：PUB <topic>\n + 4 字节大端 body 长度 + body，等待 OK；E_* 错误帧转为 ProtocolException
  • 消费：SUB <topic> <channel>\n，每次阻塞读取前发送 RDY 1\n
  • 帧格式：4 字节大端 size（含 4 字节 frame type）+ 4 字节 type + payload
  • type 0 = response（OK、_heartbeat_）
  • type 1 = error（E_*）
  • type 2 = message（8 字节纳秒时间戳 + 2 字节 attempts + 16 字节 message id + body）
  • 心跳：读到 _heartbeat_ 立即回 NOP\n
  • 确认：FIN <id>\n；重投：REQ <id> <delayMs>\n

限制

  • channel 必须先存在：NSQ 只把消息投递给发布时已存在的 channel。驱动在首次 receive() 时惰性 SUB 创建 channel，因此「先发布、后首次订阅」的消息会丢失。消费者进程应先调用一次 receive()（可用短超时）完成订阅，再开始发布/消费；集成测试即按此顺序验证。
  • 发布无 message id：NSQ 在投递时才生成 16 字节 id，PublishResult::id 恒为 null。
  • 拉取模型与心跳：驱动只在 receive()/握手/等待发布应答期间读取 socket 并回应心跳。若两次 receive() 之间（或处理消息期间）超过 nsqd 心跳超时（默认约 60 秒），消费连接会被 broker 关闭，之后 ack()/reject() 或下一次 receive() 抛 ConnectionException。长任务请缩短轮询间隔，或调大 nsqd --heartbeat-interval。
  • 发布连接空闲：发布连接空闲超过约 60 秒同样会被 nsqd 关闭。此时本次 publish() 抛 ConnectionException，驱动会丢弃旧连接，下一次调用自动重连；不会自动重试，以免产生重复消息。
  • 超时不破坏连接：读取超时返回 null，已读到的半帧保留在缓冲区，下一次 receive() 继续解析；超时不会关闭连接。
  • 不支持 TLS、AUTH、ephemeral channel、DPUB、TOUCH、消息体压缩。

Redis Streams 驱动

驱动名：redis。纯 PHP 实现 RESP2 协议，不依赖 phpredis / Predis 扩展。

配置

PHP
'connections' => [
    'redis' => [
        'driver' => 'redis',
        'host' => '127.0.0.1',
        'port' => 6379,
        'password' => null,
        'database' => 0,
        'group' => 'messaging',
        'consumer' => 'worker-1',
        'max_length' => null,
        'timeout' => 5.0,
    ],
],
键 必填 默认 说明
host 是 — Redis 主机名或 IP
port 否 6379 端口
password 否 null 非空时连接后发送 AUTH
database 否 0 非 0 时连接后发送 SELECT
group 否 messaging 消费者组名
consumer 否 <hostname>-<pid> 消费者名
max_length 否 null 设置后 XADD 携带 MAXLEN ~ n（近似裁剪）
timeout 否 5.0 连接超时（秒）

目的地（publish / receive 的第一个参数）即 Redis Stream 的 key。

能力

能力 值 说明
ack ✓ XACK
requeue ✗ 见下方限制
delay ✗ 消息带 delayMs 时抛 UnsupportedFeatureException
consumerGroups ✓ XGROUP / XREADGROUP
batchPublish ✓ 逐条 XADD
ordering ✓ Stream 内按 ID 有序
headers ✓ JSON 存于 headers 字段

行为

  • 首次接收某个 stream 时执行 XGROUP CREATE <stream> <group> 0 MKSTREAM；从 0 开始，首次消费会包含此前积压的消息， BUSYGROUP 视为成功。发布本身不创建消费者组。
  • publish 使用 XADD <stream> [MAXLEN ~ n] * body <body> [headers <json>] [key <key>]， 返回的 stream ID 即 PublishResult::id。
  • receive 使用 XREADGROUP GROUP <group> <consumer> COUNT 1 BLOCK <timeoutMs> STREAMS <stream> >。 timeoutMs = 0 时 BLOCK 0（服务端无限等待）；超时返回 null。
  • ack() 执行 XACK；reject(false) 同样执行 XACK（丢弃）。
  • 消息 attempts() 恒为 1：XREADGROUP 不暴露投递次数。

限制

  • reject(true) 抛 UnsupportedFeatureException。Redis Streams 无法同步重新入队； 未 XACK 的消息留在 PEL（Pending Entries List）中。恢复策略由使用方实现： 用 XAUTOCLAIM（Redis 6.2+）或 XPENDING + XCLAIM 把超时未确认的消息转移给其他消费者。
  • 无延迟消息、无 TLS 配置项（v1 仅明文 TCP）。
  • 每次 receive 最多取一条消息（COUNT 1）。
  • max_length 使用 MAXLEN ~ n 近似裁剪：Redis 按内部宏节点整块裁剪， 小流可能暂时保留多于 n 条，属预期行为；需要精确上限请改用 MAXLEN n 语义。
  • 连接断开后不自动重连。

示例

PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Manager;

$mq = new Manager([
    'default' => 'redis',
    'connections' => [
        'redis' => ['driver' => 'redis', 'host' => '127.0.0.1', 'group' => 'orders'],
    ],
]);

$mq->extend('redis', new Erikwang2013\Messaging\Driver\Redis\RedisStreamsFactory());

$connection = $mq->connection();
$connection->publish('orders', Message::json(['id' => 1], ['trace' => 'abc']));

while ($message = $connection->receive('orders', new ReceiveOptions(5000))) {
    handle($message->body());
    $message->ack();
}

Azure Service Bus 驱动

驱动名：azure-service-bus。纯 PHP 实现 Azure Service Bus data-plane REST 接口， 使用 Shared Access Signature（SAS）认证，不依赖 azure-service-bus SDK 或 AMQP 扩展。 HTTP 使用 Guzzle，HMAC 使用 hash_hmac（ext-hash，PHP 默认启用）。

  • 工厂类：Erikwang2013\Messaging\Driver\Azure\ServiceBusFactory
  • 驱动类：Erikwang2013\Messaging\Driver\Azure\ServiceBusDriver
  • SAS 签名：Erikwang2013\Messaging\Driver\Azure\SasToken

官方文档（实现依据，2026-10 核对）： Send Message、 Peek-Lock Message、 Delete Message（complete）、 Unlock Message（abandon）、 SAS token 生成、 HTTP message headers and properties。

配置

PHP
use Erikwang2013\Messaging\Driver\Azure\ServiceBusFactory;
use Erikwang2013\Messaging\Manager;

$mq = new Manager([
    'default' => 'azure',
    'connections' => [
        'azure' => [
            'driver' => 'azure-service-bus',
            'namespace' => 'my-namespace',            // 与 endpoint 二选一
            // 'endpoint' => 'https://my-namespace.servicebus.windows.net',
            'queue' => 'orders',                       // queue 或 topic+subscription 二选一
            // 'topic' => 'events',
            // 'subscription' => 'workers',
            'shared_access_key_name' => 'RootManageSharedAccessKey',
            'shared_access_key' => '...base64 key from the portal...',
            'timeout' => 30.0,
        ],
    ],
]);
$mq->extend('azure-service-bus', new ServiceBusFactory());
键 必填 默认 说明
namespace 与 endpoint 二选一 — 生成 https://{namespace}.servicebus.windows.net
endpoint 与 namespace 二选一 — 显式 API 根地址；允许 http://（仅测试/代理），主机名会转小写
queue 与 topic 二选一 — 默认队列；发布和接收都使用它
topic 与 queue 二选一 — 与 subscription 同时提供；发布到 topic，从 subscription 接收
subscription 与 topic 成对 — 订阅名
shared_access_key_name 是 — 授权规则名（Policies → Shared access policies）
shared_access_key 是 — 授权规则的 primary/secondary key，按字符串使用，不要 base64 解码
timeout 否 30.0 普通 HTTP 超时（秒）；也是 timeoutMs = 0 时的默认接收等待时间
client 否 — 注入 GuzzleHttp\ClientInterface（测试 / DI 用）

destination 参数优先于连接级默认值：

  • 发布：传队列名或 topic 名；'' 使用连接配置。传 topic/subscriptions/sub 会抛 InvalidArgumentException。
  • 接收：传队列名，或完整订阅路径 topic/subscriptions/sub；'' 使用连接配置 （topic + subscription 模式会拼成 topic/subscriptions/sub）。
  • 实体名只允许字母、数字、.、_、~、-，且以字母或数字开头。

驱动不创建队列、topic 或 subscription，也不修改其配置，必须事先在 Azure 侧存在。

示例

PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;

$conn = $mq->connection('azure');

$conn->publish('orders', Message::json(['id' => 1], ['trace' => 'abc'], 'customer-42'));

while ($message = $conn->receive('orders', new ReceiveOptions(5000))) {
    try {
        handle($message->body(), $message->headers());
        $message->ack();              // peek-lock + Delete Message
    } catch (Throwable $e) {
        $message->reject(true);       // Unlock Message，立即可重投
    }
}

延迟发布：

PHP
$conn->publish('orders', new Message('retry', [], null, 30_000)); // 30 秒后可见

认证（SAS）

Code
SharedAccessSignature sr={urlencode(resourceURI)}&sig={urlencode(base64(HMAC-SHA256(key, urlencode(resourceURI) + "\n" + expiry)))}&se={expiry}&skn={urlencode(keyName)}
  • resourceURI 为 {endpoint}/{实体路径}（队列，或 topic 用于发布）；先转小写，再做 URL 编码后参与签名， sr= 也使用同一小写形式（Azure 按小写规范校验签名）。
  • expiry 为 UNIX 秒；token 有效期 3600 秒，剩余 300 秒时自动刷新。
  • 每个实体路径单独缓存 token；所有请求携带 Authorization: SharedAccessSignature ...。
  • key 按 Azure 门户字符串原样参与 HMAC，不做 base64 解码。
  • 支持命名空间级或实体级授权规则；订阅沿用 topic/namespace 的规则（Service Bus 不支持订阅级 SAS 规则）。

请求映射

所有消息操作都不需要 api-version 查询参数（官方文档明确说明 BrokerProperties 映射与 api-version 无关）。

操作 HTTP 路径
发布 POST {endpoint}/{queue|topic}/messages
peek-lock 接收 POST {endpoint}/{queue|topic/subscriptions/sub}/messages/head?timeout={seconds}
ack（complete） DELETE peek-lock 响应 Location 头原样地址
reject(true)（abandon） PUT peek-lock 响应 Location 头原样地址
reject(false)（丢弃） DELETE 同上，等价 complete
  • 发布：Content-Type: text/plain（可用 ContentType / Content-Type 头覆盖）， BrokerProperties 头为 JSON；自定义属性作为独立 HTTP 头。请求体为原始字节。
  • 接收：201 返回消息和 BrokerProperties（含 MessageId、LockToken、DeliveryCount、 SequenceNumber 等）；204 表示等待超时，receive() 返回 null。 timeoutMs 向上取整为秒，最小 1 秒；timeoutMs = 0 使用配置的 timeout（默认 30 秒）。
  • 驱动优先使用响应 Location 头完成 settle；缺失时才用 MessageId/SequenceNumber + LockToken 拼路径。

BrokerProperties 与 headers

来源 去向
Message::key BrokerProperties.CorrelationId；接收时反向映射为 key()
Message::delayMs BrokerProperties.ScheduledEnqueueTimeUtc = now + delayMs（秒级精度）
Label / CorrelationId / ReplyTo / ReplyToSessionId / To / SessionId / PartitionKey 对应 BrokerProperties（字符串）
TimeToLive BrokerProperties.TimeToLive（正整数秒）
ScheduledEnqueueTimeUtc BrokerProperties.ScheduledEnqueueTimeUtc（HTTP-date、UNIX 时间戳或 DateTimeInterface）
MessageId 覆盖驱动生成的 32 位十六进制 id
ContentType / Content-Type HTTP Content-Type（不出现在接收端 headers）
其他 header 自定义消息属性，逐个头传输
  • 自定义 header 值支持 string / int / float / bool。字符串会加引号发送（避免 Service Bus 把 "123" 推断为整数）；接收时按官方类型规则还原。
  • Authorization、BrokerProperties、x-ms-*、Host、Content-Length 等保留头会抛 InvalidArgumentException，不会静默丢弃。数组/对象值同样抛异常。
  • Message::key 与 CorrelationId 头同时出现且值不同会抛异常。
  • 接收端 headers() 只包含自定义属性；系统属性在 raw()['broker_properties']， Location/Content-Type/状态码在 raw() 的其他键中。
  • raw() 结构：['broker_properties' => array, 'location' => string, 'status' => int, 'content_type' => string]。

能力

能力 值 说明
ack ✓ DELETE（Delete Message / complete）
requeue ✓ PUT（Unlock Message）；立即可重投，DeliveryCount 递增
delay ✓ 发布时 ScheduledEnqueueTimeUtc（秒级精度）
consumer group ✗ 通过 topic + subscription 在 broker 侧配置，驱动不管理
batch publish ✗ 仅单条发送；publishBatch() 抛 UnsupportedFeatureException
ordering ✗ 不实现 session；SessionId 头仅透传，不保证 FIFO
headers ✓ 自定义属性 + 常用 BrokerProperties
requiresActiveSubscription ✗ 队列/订阅需预先存在，但无需先调用 receive()

限制

  • 仅 REST + SAS：不支持 AMQP、Microsoft Entra ID（OAuth）认证、事务、send-via、会话（FIFO）、 重复检测管理、主题规则管理、订阅自动创建。
  • 不做自动重试：429/5xx 直接抛 RequestException；重复投递由 Service Bus 至少一次语义决定， 消费端需幂等。
  • peek-lock 锁期：默认锁期由实体配置决定；长任务需在锁过期前完成，或自行调用 Renew-Lock（本驱动未封装）。锁过期后 complete/abandon 会返回 404。
  • reject(false) 是丢弃（complete），不是 dead-letter。REST data-plane 没有 dead-letter 操作； 需要 DLQ 时请依赖 MaxDeliveryCount 或 Azure 侧策略。
  • 延迟精度为秒：delayMs 向上取整；reject(true) 不支持附带冷却时间，立即重投。
  • 批量发送未实现（REST 有 Send Message Batch，本驱动未封装）。
  • 接收是同步 HTTP 长轮询：timeoutMs = 0 时单次最多等待配置的 timeout（默认 30 秒）， 返回 null 后由 consume() 循环；高吞吐场景建议多进程并行。
  • Service Bus emulator 不支持 REST data-plane，因此集成测试默认使用内存假传输； 真实 Azure 测试为可选，且队列必须预建。
  • 实体名大小写不敏感；请求路径保留调用方传入的大小写，但 SAS 始终用小写规范化的资源 URI 签名。
  • 自定义 header 名按 HTTP 语义大小写不敏感；返回时保留服务端返回的写法。

Google Cloud Pub/Sub 驱动

驱动名：gcp-pubsub。纯 PHP 实现 Google Cloud Pub/Sub v1 REST JSON API，服务账号 JWT（RS256）认证， 不依赖 google/cloud-pubsub。HTTP 使用 Guzzle，签名使用 ext-openssl。

  • 工厂类：Erikwang2013\Messaging\Driver\Gcp\GcpPubSubFactory
  • 驱动类：Erikwang2013\Messaging\Driver\Gcp\GcpPubSubDriver

配置

PHP
'connections' => [
    'pubsub' => [
        'driver' => 'gcp-pubsub',
        'project_id' => 'my-project',                  // 必填
        'credentials_file' => '/etc/gcp/sa.json',      // 与 credentials_json 二选一
        // 'credentials_json' => '{...service account JSON...}',
        'subscription' => 'orders-default',            // 可选：receive('') 的默认订阅
        'ack_deadline_seconds' => 60,                  // 可选：拉取后延长租约（秒），0 关闭
        'endpoint' => 'https://pubsub.googleapis.com', // 可选
        'timeout' => 30.0,                             // 可选：普通请求超时（秒）
    ],
],
键 必填 默认 说明
project_id 是 — GCP 项目 ID
credentials_file 二选一 — 服务账号 JSON 文件路径
credentials_json 二选一 — 服务账号 JSON 字符串（也接受已解析的数组）
emulator_host 否 null 如 127.0.0.1:8085；设置后使用 http:// 且不认证
endpoint 否 https://pubsub.googleapis.com API 根地址；显式设置时优先于 emulator 推导值
subscription 否 null receive('') 时使用的订阅名
ack_deadline_seconds 否 60 拉取到消息后调用 :modifyAckDeadline 延长租约的秒数，整数 0–600；0 关闭这次额外请求
timeout 否 30.0 发布、ack、租约续期、token 交换的 HTTP 超时（秒）；receive() 的 pull 请求使用调用方超时

publish() 的 destination 是 topic，receive() 的 destination 是 subscription。 Pub/Sub 不要求两者同名，但集成测试使用同名资源以便复用契约测试。 驱动不会创建 topic/subscription，二者必须事先存在。

示例

PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Driver\Gcp\GcpPubSubFactory;
use Erikwang2013\Messaging\Manager;

$mq = new Manager([
    'default' => 'gcp',
    'connections' => [
        'gcp' => [
            'driver' => 'gcp-pubsub',
            'project_id' => 'my-project',
            'credentials_file' => '/etc/gcp/sa.json',
        ],
    ],
]);
$mq->extend('gcp-pubsub', new GcpPubSubFactory());

$conn = $mq->connection();
$conn->publish('orders', Message::json(['id' => 1], ['trace' => 'abc'], 'customer-42'));

while ($message = $conn->receive('orders-subscription', new ReceiveOptions(5000))) {
    handle($message->body(), $message->headers());
    $message->ack();
}

认证

  • 从服务账号 JSON 读取 client_email、private_key、private_key_id。
  • 构造 JWT：{iss, scope: https://www.googleapis.com/auth/pubsub, aud: https://oauth2.googleapis.com/token, iat, exp}， exp = iat + 3600，用 OPENSSL_ALGO_SHA256 做 RS256 签名。
  • 以 grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer 调用 https://oauth2.googleapis.com/token 换取 access token，并缓存到 expires_in - 60s；到期前 60 秒自动刷新。
  • 所有 Pub/Sub 请求携带 Authorization: Bearer <token>。
  • emulator_host 设置时完全跳过 token 交换（模拟器不校验认证）。

能力

能力 值 说明
ack ✓ subscriptions/{sub}:acknowledge
requeue ✓ reject(true) 调 :modifyAckDeadline 且 ackDeadlineSeconds: 0，立即重新投递；reject(false) 等价 ack（丢弃）
delay（发布） ✗ 消息带 delayMs 抛 UnsupportedFeatureException
consumer group ✓ Pub/Sub subscription 天然为多消费者竞争消费
batch publish ✓ 一次 HTTP 调用携带全部 messages，逐条返回 messageIds[i]
ordering ✓ Message::$key 映射为 orderingKey
headers ✓ 映射为 Pub/Sub 字符串 attributes；非标量值抛 UnsupportedFeatureException，不会静默丢弃
requiresActiveSubscription ✗ 无需先调用 receive()；但 subscription 必须由外部创建

ReceivedMessage::attempts() 恒为 1：Pub/Sub 只有在配置 dead-letter policy 时才暴露 deliveryAttempt，驱动 v1 不管理该策略。

行为

  • 发布：POST /v1/projects/{project}/topics/{topic}:publish， body {"messages":[{"data": base64(body), "attributes": {...}, "orderingKey": key}]}。 PublishResult::id 为服务端返回的 messageIds[i]。
  • 接收：POST /v1/projects/{project}/subscriptions/{sub}:pull， body {"maxMessages":1, "returnImmediately":false}，返回 receivedMessages[0]。
  • 拉取成功后、返回 ReceivedMessage 前，若 ack_deadline_seconds > 0，先调用 :modifyAckDeadline 把该消息租约延长到配置秒数（默认 60），避免处理时间超过订阅默认 ack deadline（通常 10 秒）而被重复投递。每次成功拉取因此多一次 HTTP 请求。
  • timeoutMs > 0：在该期限内轮询（每次请求以剩余时间作为 HTTP 超时），期限内无消息返回 null。
  • timeoutMs = 0：循环长轮询（单次 HTTP 超时 95 秒，Pub/Sub 服务端约 90 秒返回空响应）， 直到收到消息；网络错误抛 ConnectionException。
  • 确认/重投：ack() → :acknowledge；reject(true) → :modifyAckDeadline（0 秒）； reject(false) → :acknowledge。
  • 错误映射：HTTP 401/403 → AuthenticationException；其他非 2xx → RequestException （含 statusCode() 与 responseBody()）；连接失败 → ConnectionException；响应非法 JSON → ProtocolException。
  • 不做自动重试，避免产生重复消息。

限制

  • 仅 REST pull，不使用 streaming pull：每条 receive() 最多取一条消息；高吞吐场景建议多进程/多 worker 并行拉取。
  • 长任务受租约限制：消息必须在 ack_deadline_seconds（默认 60 秒，最大 600）内处理完并 ack/reject，否则 Pub/Sub 会重新投递并产生重复。处理更久请调大该值；超过 600 秒需拆分任务或 自行实现续租（驱动不在处理期间再次续租）。
  • 无 exactly-once：Pub/Sub 默认至少一次投递；重复消息需消费端自行幂等。
  • 不管理 dead-letter policy：订阅的 dead-letter 配置需在 GCP 侧预建，驱动不读取 deliveryAttempt。
  • 不管理 topic/subscription：不自动创建、不自动删除；receive() 对不存在的订阅返回 RequestException（404）。
  • 无延迟发布、无 schema、无 push 订阅、无 seek/snapshot。
  • 顺序性依赖 orderingKey + 订阅侧开启 message ordering；驱动只负责传递 key，不修改订阅配置。
  • header（attribute）值必须可转为字符串；数组/对象会抛异常而不是被丢弃。
  • timeoutMs = 0 的阻塞拉取会持续循环，直到收到消息或抛连接错误，驱动内部无法取消； 需要可中断的消费循环时请使用有限超时并在业务层检查退出条件。
  • 明文 HTTP 仅用于模拟器；真实服务走 HTTPS。

AWS Kinesis 驱动

驱动名：kinesis。纯 PHP 实现 Kinesis Data Streams JSON API 与 SigV4 签名，不依赖 aws/aws-sdk-php。

Kinesis 是分片、可重放的消息流，没有队列式 ack/requeue。本驱动用游标（checkpoint）表达消费进度： ack() 记录该分片已消费到的序列号，下次 receive() 从该位置之后继续读取。

配置

kinesis 已内置于 Manager 的驱动表，直接取连接即可：

PHP
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'kinesis',
    'connections' => [
        'kinesis' => [
            'driver' => 'kinesis',
            'region' => 'us-east-1',                       // 必填
            'access_key' => 'AKIA...',                     // 可省略，回退到 AWS_ACCESS_KEY_ID
            'secret_key' => '...',                         // 可省略，回退到 AWS_SECRET_ACCESS_KEY
            'session_token' => null,                       // 可选，或 AWS_SESSION_TOKEN
            'endpoint' => null,                            // 可选，AWS 兼容端点（本地 Moto：http://127.0.0.1:5000）
            'timeout' => 30.0,                             // HTTP 超时（秒），默认 30.0
            'checkpoint' => null,                          // 可选 callable(string $stream, string $shard, string $sequence)
        ],
    ],
]);
$conn = $manager->connection('kinesis');

destination 是流名称（如 orders），不是 ARN。流必须已存在且状态为 ACTIVE。

能力

能力 支持 说明
ack ✗ 无队列式删除；ack() 仅推进内存游标并触发 checkpoint 回调
requeue ✗ 无重投；reject() 抛 UnsupportedFeatureException
delay（发布） ✗ 传入 delayMs 抛 UnsupportedFeatureException
consumer group ✗ 使用分片迭代器，无消费者组
batch publish ✓ PutRecords，单次最多 500 条（驱动会校验）
ordering ✓ 同一分区键（PartitionKey）内有序，按分片保序
headers ✗ Kinesis 消息无属性；headers 非空时抛 UnsupportedFeatureException

行为

  • 发送：PutRecord，Data 为原始 body 的 base64（二进制安全），PartitionKey 来自 Message::key；未提供时随机生成 16 字节十六进制串。PublishResult::id 为 SequenceNumber。
  • 批量：PutRecords，按输入顺序返回等长结果；部分失败项 id 为 null，raw 为失败条目 （含 ErrorCode / ErrorMessage），并记录 warning 日志。
  • 接收：ListShards 获取分片，首次从 TRIM_HORIZON（或已有 checkpoint 的 AFTER_SEQUENCE_NUMBER）取 GetShardIterator，GetRecords 每批最多 100 条并缓冲。 一次 receive() 返回一条；缓冲区为空时按 timeoutMs 轮询。
  • ReceivedMessage::id() 为序列号，key() 为 PartitionKey，attempts() 恒为 1。
  • ack() 将 [流, 分片, 序列号] 写入内存游标并调用 checkpoint 回调；同一分片后续从该序列号之后读取。
  • 迭代器过期（ExpiredIteratorException）时自动按当前 checkpoint 重建；NextShardIterator 为空表示 分片已关闭，驱动会定期重新 ListShards 以发现新分片。
  • 超时/连接失败/HTTP 错误映射与其他 AWS 驱动一致。

限制

  • checkpoint 只在内存中：进程退出后丢失，重新从 TRIM_HORIZON 读取；需要持久化时通过 checkpoint 回调自行写入 Redis/数据库，并在启动时先 receive() 前回填不可行——本驱动不支持 从外部注入初始 checkpoint，需扩展驱动或在回调侧做去重。这是当前实现最重要的限制。
  • 不支持 SequenceNumberForOrdering、KPL 聚合、增强型扇出（enhanced fan-out）、跨账户消费。
  • 多消费者共享同一流时没有租约/协调，每个实例各自读取全部数据；需要消费者组语义请使用其他驱动。
  • reject() 不支持；没有死信队列概念。
  • 不检查流是否存在或 ACTIVE，由 AWS 返回错误；不管理分片扩缩容，重新 ListShards 只在无活跃分片时发生。
  • headers 与 delay 不受支持（抛 UnsupportedFeatureException）。

            'secret_key' => '...',                         // 可省略，回退到 AWS_SECRET_ACCESS_KEY

能力 支持 说明
ack ✗ 发布后无确认/重投语义
requeue ✗ 同上
delay（发布） ✗ SNS 的 DelaySeconds 未使用；传入 delayMs 抛 UnsupportedFeatureException
consumer group ✗ 无消费概念

  • 使用 Query 协议：POST /，Content-Type: application/x-www-form-urlencoded， Action=Publish&Version=2010-03-31&TopicArn=...&Message=...。

  • 仅支持 Publish。创建/删除 Topic、Subscribe/Unsubscribe、SetSubscriptionAttributes 等管理操作 不在驱动范围内，需要时可用 AwsHttpClient::query()（集成测试即如此）。
  • 不支持 FIFO Topic（无 MessageGroupId / deduplication id）、不支持 MessageStructure=json、 不支持 SMS 直发。
  • Message 建议为 UTF-8 文本；SNS 对无效 UTF-8 的消息体不作保证，驱动不做转码。
  • 属性名规则与 SQS 相同：1–256 个 A-Z a-z 0-9 _ . -，不能以点开头/结尾，不能是 AWS. / Amazon. 前缀。

驱动名：sqs。纯 PHP 实现 AWS SQS JSON 协议与 SigV4 签名，不依赖 aws/aws-sdk-php。

sqs 已内置于 Manager 的驱动表，直接取连接即可：

$manager = new Manager([

            'secret_key' => '...',                         // 可省略，回退到 AWS_SECRET_ACCESS_KEY

能力

能力 支持 说明
ack ✓ DeleteMessage
requeue ✓ reject(true) 执行 ChangeMessageVisibility 0；reject(false) 等同 ack（删除）
delay（发布） ✓ delayMs 向上取整为 DelaySeconds（0–900）；FIFO 队列不支持，抛 UnsupportedFeatureException
consumer group ✗ SQS 无消费者组；多消费者天然竞争消费
batch publish ✓ SendMessageBatch，单次最多 10 条
ordering ✗ 标准队列不保证顺序；FIFO 队列仅在提供 Message::key 时按 MessageGroupId 有序
headers ✓ MessageAttributes，最多 10 个；标量走 String，二进制或结构走 Binary

ReceivedMessage::attempts() 来自 ApproximateReceiveCount（首次投递为 1）。 Message::key 映射为 MessageGroupId，仅在 FIFO 队列上可用；收到 FIFO 消息时 key() 返回 MessageGroupId。

  • receive() 的长轮询 WaitTimeSeconds 由 timeoutMs 推导（0–20 秒）；timeoutMs = 0 表示无限阻塞。 timeoutMs 小于 1 秒时使用短轮询，未取到消息则等到超时后返回 null。
  • 每次接收请求 MaxNumberOfMessages = 1，并请求 AttributeNames = All 与 MessageAttributeNames = All。
  • publishBatch() 返回与输入等长的 PublishResult 列表；部分失败时对应项 id 为 null， raw 为失败条目（含 Code / Message），并记录 warning 日志。
  • HTTP 403/401 映射为 AuthenticationException；其余错误状态映射为带 statusCode() / responseBody() 的 RequestException；连接失败与超时分别映射为 ConnectionException / TimeoutException。

限制

  • 消息体必须是合法 UTF-8：SQS 的 MessageBody 是字符串，二进制负载不支持。非 UTF-8 body 或空 body 在发送前抛 InvalidArgumentException，不会静默转码。

  • FIFO 不支持逐条延迟：FIFO 队列上带 delayMs 抛 UnsupportedFeatureException。
  • 不校验 256 KiB 消息上限、不管理死信队列 / 队列属性 / 标签；这些由 AWS 报错并映射为 RequestException。
  • 不支持 SQS 的 PurgeQueue、ListQueues 等管理操作；集成测试通过内部 AwsHttpClient 调用管理 API。
  • 消息属性名需为 1–256 个 A-Z a-z 0-9 _ . -，不能以点开头/结尾，且不能使用 AWS. / Amazon. 前缀。

RabbitMQ 驱动

纯 PHP 实现的 AMQP 0-9-1 客户端，直接基于 TCP/TLS 收发协议帧，不依赖 ext-amqp 或 php-amqplib。目标（destination）即队列名，消息通过默认交换机发布。

配置

键 类型 默认 说明
host string 必填 服务器地址
port int 5672（tls=true 时 5671） AMQP 端口
username string guest SASL PLAIN 用户名
password string guest SASL PLAIN 密码
vhost string / 虚拟主机
heartbeat int 60 心跳间隔秒数，0 关闭心跳
timeout float 5.0 连接与命令响应超时，秒
tls bool false 使用 TLS 连接（tls://）
tls_context array [] 透传给 stream_context_create() 的 SSL 上下文，例如 ['ssl' => ['cafile' => '/path/ca.pem']]
durable bool true queue.declare 的 durable 标志，同时决定发布消息的 delivery-mode（durable 时 2）
prefetch int 1 basic.qos 的 prefetch count，0 表示不限
PHP
use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Driver\RabbitMq\RabbitMqFactory;
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'queue',
    'connections' => [
        'queue' => [
            'driver' => 'rabbitmq',
            'host' => '127.0.0.1',
            'port' => 5672,
            'username' => 'guest',
            'password' => 'guest',
            'vhost' => '/',
        ],
    ],
]);
$manager->extend('rabbitmq', new RabbitMqFactory());

$connection = $manager->connection();
$connection->publish('orders', new Message('payload', ['trace' => 'abc'], 'order-1'));

$message = $connection->receive('orders', new ReceiveOptions(5000));
if ($message !== null) {
    try {
        handle($message->body(), $message->headers());
        $message->ack();
    } catch (Throwable $e) {
        $message->reject(true);
    }
}

能力

能力 支持 说明
ack ✓ basic.ack
requeue ✓ reject(true) 发送 basic.nack requeue=true；reject(false) 发送 basic.nack requeue=false
delay ✗ 需要 rabbitmq_delayed_message_exchange 插件，本驱动未实现；Message::delayMs 非空时抛 UnsupportedFeatureException
consumer groups ✗ 同一队列上的消费者天然竞争消费
batch publish ✗ 抛 UnsupportedFeatureException
ordering ✗ 单队列通常 FIFO，但协议不承诺
headers ✓ 通过 application_headers 字段表原样往返

语义

  • 目标即队列：publish() 与 receive() 都会幂等执行 queue.declare（durable 由配置决定），发布到默认交换机 ''，routing key 等于队列名。
  • 消息 ID：发布时生成 32 位十六进制 ID 写入 message-id，PublishResult::$id 与接收到的 ReceivedMessage::id() 一致。其他客户端未设置 message-id 时，id() 为 null。
  • key：Message::$key 写入 correlation-id；接收时优先取 correlation-id，缺失时回退为 delivery 的 routing key。
  • headers：支持 string、int（自动选择 32/64 位）、float、bool、null、嵌套表与数组。其他类型（对象、资源）在发布时抛 InvalidArgumentException，不会静默丢弃。
  • 接收：首次 receive() 对目标队列发起 basic.consume（no-ack=false），后续投递在驱动内缓冲，按到达顺序返回。timeoutMs=0 永久阻塞；timeoutMs>0 到期返回 null。服务器要求的心跳帧在等待期间自动应答，客户端也按协商间隔发送心跳。
  • 确认：ack() 使用投递时的 delivery tag 发送 basic.ack；attempts() 固定为 1，不读取 x-death 等重投计数。
  • 连接：工厂在 Manager::connection() 时立即完成握手并应用 basic.qos，认证或端点错误当场抛出。连接惰性复用，不做自动重连。
  • 关闭：close() 发送 connection.close（200）后关闭套接字；已声明的队列保留。

协议范围

  • 协议头 AMQP\x00\x00\x09\x01；SASL PLAIN。
  • 帧类型：method（1）、header（2）、body（3）、heartbeat（8），帧尾 0xCE；短字符串、长字符串、字段表、bit、大端整数编解码。
  • 方法：connection.start/start-ok、tune/tune-ok、open/open-ok、close/close-ok、blocked/unblocked；channel.open/open-ok/close/close-ok；queue.declare/declare-ok；basic.qos/qos-ok、basic.consume/consume-ok/cancel、basic.publish、basic.deliver、basic.ack、basic.nack；basic.return 与 publisher confirm 的 basic.ack/nack 会被识别但不启用。
  • 内容帧按协商的 frame-max 自动分片；body 二进制安全。
  • 心跳按 AMQP 规则协商：任一方为 0 即关闭，否则取二者最小值；空闲时发送心跳并忽略收到的空心跳帧。
  • TLS 使用 tls:// 流，端口默认 5671，tls_context 透传 SSL 选项。

限制

  • 只使用默认交换机与队列名路由：不支持自定义 exchange、binding、topic/fanout 路由与 basic.get。
  • 未启用 publisher confirm；basic.publish 写入套接字即返回。队列已声明，因此默认交换机路由存在，但 broker 侧异步失败不会反馈给发布者。

ZeroMQ 驱动

驱动名：zeromq · 命名空间：Erikwang2013\Messaging\Driver\ZeroMq · 实现：ZeroMqDriver / ZeroMqFactory

当前实现范围：ZMTP 3.1 + NULL 机制，支持 PUB/SUB 与 PUSH/PULL 两种模式。纯 PHP 实现，不依赖 ext-zmq。ZeroMQ 是 brokerless、至多一次的：没有持久化、ack、重投、延迟和消费者组。

配置

键 必填 默认 说明

use Erikwang2013\Messaging\Contract\Message;
use Erikwang2013\Messaging\Contract\ReceiveOptions;
use Erikwang2013\Messaging\Manager;

$mq = new Manager([
    'default' => 'zmq',
    'connections' => [
        'zmq' => [
            'driver' => 'zeromq',
            'host' => '127.0.0.1',
            'port' => 5555,
            'pattern' => 'pubsub',
        ],
    ],
]);
$connection = $mq->connection();

// 订阅端：先注册 topic 前缀（PUB/SUB 只向已存在的订阅投递）
$connection->receive('orders.created', new ReceiveOptions(10));
$message = $connection->receive('orders.created', new ReceiveOptions(1000));

// 发布端
$connection->publish('orders.created', new Message('hello'));

publish() 与 receive() 各自懒建立一条 TCP 连接：PUB/SUB 模式下分别是 PUB 与 SUB，PUSH/PULL 模式下分别是 PUSH 与 PULL。真实 libzmq 端点通常只绑定一种 socket 类型，所以同一个实例既要发布又要接收时，对端必须是能同时接受两种角色的中继/网关；只使用单一角色的实例只建立一条连接。

delay false Message::$delayMs 非空时抛 UnsupportedFeatureException

协议范围

  • 握手：发送 64 字节 greeting（0xFF + 8 字节填充 + 0x7F + 版本 3.1 + 20 字节 NULL + as-server 0 + 31 字节填充），读取并校验对端 greeting；随后交换 READY 命令帧，校验 Socket-Type 是否兼容（PUB↔SUB、PUSH↔PULL）。
  • 帧：1 字节 flags（MORE 0x01、LONG 0x02、COMMAND 0x04）+ 1 或 8 字节大端长度 + body。带 MORE 的连续帧重组为一条消息；body 二进制安全，支持零长度和超过 255 字节（自动使用 LONG）。
  • PUB/SUB：SUB 为每个 destination 发送订阅帧 0x01 + topic 前缀；发布时线上 body 为 destination . body，接收时按最长匹配的已订阅前缀剥离。PUB/SUB 过滤由对端（PUB socket）完成，驱动不做客户端过滤；收到不匹配任何订阅的消息抛 ProtocolException。
  • PUSH/PULL：没有 topic，destination 不写入线上，body 原样发送；PUSH 端由对端在 PULL 连接之间负载均衡。
  • receive() 的 timeoutMs 为 0 时一直阻塞，超时返回 null；握手超时抛 TimeoutException，连接失败/对端关闭抛 ConnectionException，畸形 greeting/帧/元数据抛 ProtocolException。
  • 不为每条消息生成 id；PublishResult::$id 为 null。

语义与限制

  • 至多一次：消息只存在于 TCP 缓冲区，订阅者离线、慢消费或对端重启都会丢失消息，没有重放。
  • 有界缓冲：receive() 会为其他已订阅 destination 暂存消息，每个 destination 最多 buffer_limit 条，超限抛 ProtocolException。缓冲仅在内存中，close() 或进程退出后丢失，不会持久化。
  • 慢加入（slow joiner）：SUB 的订阅需要先到达 PUB 端；先发布后订阅会丢消息。请使用独立的订阅进程并先完成首次 receive()（或短 timeout 调用）再发布。
  • topic 是消息前缀：这是 ZeroMQ PUB/SUB 的原生过滤语义。第三方发布者必须把 topic 放在 body 开头；receive() 会剥离子服务最长匹配的订阅前缀作为消息 body。若两个 destination 存在前缀关系（如 orders 与 orders.eu），按最长匹配路由。
  • 同一实例双连接：因为一个 ZeroMQ socket 只有一种角色，同时发布和接收会向同一 host:port 建立两条独立连接。多数 libzmq 端点无法在同一端口同时提供 PUB 与 SUB（或 PUSH 与 PULL），生产环境请让发布端、订阅端分别指向对端，或部署一个双角色中继/网关。
  • 不支持 bind/listen（驱动只作为连接方）、TLS、CURVE/PLAIN 机制、READY 之后的心跳/命令帧、断线重连和 socket monitor；需要这些能力时请使用 ext-zmq 或代理。
  • headers、key、delay、批量发布均不支持且不会静默丢弃：调用会抛 UnsupportedFeatureException。
  • ReceivedMessage 的 id() / key() 为 null、attempts() 恒为 1；raw() 包含 destination（PUB/SUB）与 frames（原始帧列表）。

Kafka 驱动

纯 PHP 实现的 Kafka wire protocol 客户端（Erikwang2013\Messaging\Driver\Kafka），不依赖 rdkafka 或官方 SDK。同一套实现通过别名覆盖 Kafka、Redpanda、AutoMQ、Confluent Platform 与 Azure Event Hubs（Kafka 端点）。

配置

PHP
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'kafka',
    'connections' => [
        'kafka' => [
            'driver' => 'kafka',
            'brokers' => ['127.0.0.1:9092'], // 必填，host:port 数组或逗号分隔字符串
            'group_id' => 'messaging',       // 消费组，默认 messaging
            'client_id' => 'messaging-php',  // 默认 messaging-php
            'timeout' => 10.0,               // 连接与普通请求读超时（秒），默认 10.0
            'tls' => false,                  // 默认 false
            'tls_context' => [],             // 透传给 Socket 的 SSL context 选项
            'auto_offset_reset' => 'latest', // earliest 或 latest，默认 latest
            'acks' => 1,                     // 1 或 -1 (all)，默认 1
            'fetch_max_wait_ms' => 500,      // 单次 Fetch 的最大等待，默认 500
            'session_timeout_ms' => 10000,   // 消费组会话/重平衡超时，默认 10000
            'max_poll_records' => 1,         // 每个分区每次预取并缓存的记录数，默认 1
        ],
    ],
]);

$conn = $manager->connection('kafka');

brokers 中的条目可以省略端口，此时使用驱动别名的默认端口：eventhubs 为 9093，其余（kafka、redpanda、automq、confluent）为 9092。支持 host:port、[ipv6]:port 和裸主机名。

destination 即 Kafka topic。发布端按需连接各分区 leader；消费端使用经典 consumer group 协议，一个驱动实例对应一个消费组会话。

记录格式为 record batch magic 2（base offset、leader epoch、CRC32C、attributes、时间戳、producer id/epoch/sequence、varint 编码的 key/value/headers）。CRC32C 优先使用 hash('crc32c')（PHP 8.1+），否则使用纯 PHP 查表实现。

压缩：消费端支持 gzip（ext-zlib）；其他压缩 codec 会抛 UnsupportedFeatureException。发布端当前发送未压缩 batch（配置项里没有请求压缩开关）。

语义

  • 分区选择：带 key 时使用 Kafka 默认的 murmur2 hash（seed 0x9747b28c）对分区数取模；无 key 时在分区列表上轮询。
  • 发布确认：acks 只接受 1 或 -1。不自动重试；失败直接抛异常，重试可能产生重复消息。
  • 批量发布：按分区合并消息，每个 leader 一次 Produce；返回结果顺序与输入一致，id 为该分区 batch 的 base_offset + 批内序号。
  • 消费：每次 receive() 返回一条消息，内部按分区缓冲最多 max_poll_records 条。timeoutMs 包含加入消费组的时间；超时返回 null。
  • 提交：ack 时向 coordinator 提交 offset + 1。reject(true) 清空该分区缓冲并把读取位置回退到当前 offset，下一次 receive() 会重新拉到它；reject(false) 提交并跳过。
  • 自动重置：没有已提交 offset（或 broker 返回 OFFSET_OUT_OF_RANGE）时，按 auto_offset_reset 用 ListOffsets 取 earliest/latest。
  • 重平衡：Heartbeat 返回 REBALANCE_IN_PROGRESS / ILLEGAL_GENERATION / UNKNOWN_MEMBER_ID，或 coordinator 错误时，驱动重新 FindCoordinator、JoinGroup、SyncGroup，并按 range assignor 重新分配分区。被撤销分区的本地缓冲会丢弃；未提交的消息可能由新 owner 重新投递，因此语义是 at-least-once。
  • 心跳：按 session_timeout_ms / 3 的间隔在 receive() 循环中发送，单次 Fetch 等待也被限制在该间隔内，避免长时间 fetch 导致会话过期。
  • 关闭：close() 会尽力发送 LeaveGroup，并关闭所有 broker 连接。

限制

  • 不支持 SASL（PLAIN/SCRAM/OAUTHBEARER）和 SASL 握手；只支持明文和 TLS（tls + tls_context）。
  • 不支持事务、幂等 producer、exactly-once；producer id 固定为 -1，不发送 InitProducerId。
  • 不支持压缩发布；消费只支持 gzip，snappy/lz4/zstd 抛 UnsupportedFeatureException。
  • 不支持 CreateTopics/DeleteTopics 等 admin API；依赖 broker 的 auto.create.topics.enable=true 或预先创建 topic。
  • Tombstone（value 为 null）在消费侧会变成空字符串 ''，无法区分 null 与空 body；发布侧 Message::$body 是 string，也不能发送 tombstone。
  • 只实现了经典 consumer group 的 range assignor；不支持 cooperative-sticky、static membership（group.instance.id）、KIP-848 新消费组协议。与使用其他 assignor 的客户端混用同一个 group 可能反复重平衡或加入失败。
  • 只支持按 earliest/latest 重置 offset，不支持按时间戳查询 offset，也不支持 auto_offset_reset=none。
  • 发布失败不自动重试；调用方重试可能产生重复消息。acks=1 时 leader 故障可能丢消息。
  • receive() 的超时包含首次 JoinGroup 的等待；Kafka 默认 group.initial.rebalance.delay.ms=3000，短超时的首次调用可能返回 null 但已完成入组。集成测试因此先做一次热身调用。
  • 每个驱动实例只应有一个消费循环；PHP 同步模型下不是线程安全的。

Pulsar 驱动（实验）

纯 PHP 实现的 Apache Pulsar 二进制协议客户端（Erikwang2013\Messaging\Driver\Pulsar），不依赖 Pulsar 官方 SDK 或扩展。实验性支持：仅覆盖最小的生产/消费子集，接口和协议细节可能变化。

配置

PHP
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'pulsar',
    'connections' => [
        'pulsar' => [
            'driver' => 'pulsar',
            'service_url' => 'pulsar://127.0.0.1:6650', // 必填
            'topic' => null,                            // 可选，destination 为空时的默认 topic
            'subscription' => 'messaging',              // 默认 messaging
            'consumer_name' => null,                    // 可选，便于在 broker 端识别消费者
            'timeout' => 10.0,                          // 连接、握手、lookup、发布应答超时（秒）
            'tls' => false,                             // true 时强制 TLS，即使 service_url 是 pulsar://
            'tls_context' => [],                        // 传给 PHP stream context 的 SSL 选项
        ],
    ],
]);

$conn = $manager->connection('pulsar');

service_url 只接受单个 broker：pulsar://host:6650 或 pulsar+ssl://host:6651（默认端口分别为 6650/6651）。不支持逗号分隔的多 broker、URL 路径、用户名密码、query 或 fragment。tls_context 可传 verify_peer、cafile、local_cert 等标准 SSL context 选项。

destination 即 Pulsar topic。建议使用完整名称 persistent://tenant/namespace/topic；短名称依赖 broker 的默认 tenant/namespace 解析。驱动为每个发布/消费 topic 各保持一条独立连接。

能力

能力 支持 说明
ack ✓ 逐条 CommandAck（Individual）
requeue ✓ reject(true) 发送 CommandRedeliverUnacknowledgedMessages；reject(false) 等同 ack（丢弃）
delay（发布） ✓ deliverAfterMs 写入 MessageMetadata.deliver_at_time，由 broker 延迟投递

  • 帧格式：4 字节大端 totalSize + 4 字节大端 commandSize + protobuf BaseCommand（+ 可选 payload）
  • 命令：Connect/Connected、LookupTopic/LookupResponse（最多跟随 5 次 redirect）、Producer/ProducerSuccess、Send/SendReceipt/SendError、Subscribe/Success、Flow、Message、Ack、RedeliverUnacknowledgedMessages、CloseProducer/CloseConsumer、Ping/Pong
  • 消息帧：magic 0x0e01 + 4 字节 CRC32C + 4 字节 metadata 长度 + MessageMetadata + body；同时兼容旧协议/旧客户端的无 magic、无 checksum 格式（直接以 metadata 长度开头）
  • 协议版本：11（v11 起 broker 保留 magic/CRC 帧；更早版本会剥离）；客户端标识 messaging-php/1.0.0
  • 订阅类型：Shared（Exclusive/Failover 会忽略延迟投递）；启动位置：Earliest（见下方偏差说明）
  • 每次 receive() 最多取一条消息，按需发送 Flow(1) 许可

限制

  • 实验性：仅实现最小子集，尚未在多种 Pulsar 版本/部署形态上验证。
  • 不支持认证：TLS 传输可用，但不支持 Pulsar token、OAuth 等认证；broker 发起 AuthChallenge 时抛 AuthenticationException。
  • 不支持 batching、压缩、schema、事务、chunking：入站消息带 compression 或 batch 标记、出站 publishBatch() 均抛 UnsupportedFeatureException。
  • 不支持分区 topic 路由：驱动把 destination 当作单个 topic。对分区 topic 只能显式指定某个分区（如 ...-partition-0），不会自动跨分区发布或消费。
  • 使用 Shared 订阅：同一订阅允许多个消费者；reject(true) 发送带 message id 的 redeliver 命令，只重投被拒绝的那条消息，attempts() 由 broker 的 redelivery_count 递增。
  • 延迟投递的分辨率约 1 秒：broker 的 delayed-delivery tick 默认 1000ms；小于 tick 的延迟（例如 500ms）可能立即投递。需要可靠延迟时请使用不小于 1 秒的值。
  • 启动位置是 Earliest：这是为了让 requiresActiveSubscription=false 的契约成立（先发布、后首次 receive() 仍能收到）。Pulsar 默认是 Latest；只需要新消息的订阅应复用已有订阅名，或由 broker 端管理订阅。
  • 发布不自动重试：publish() 遇到 ConnectionException 会丢弃生产者连接，下一次调用重连。失败时消息可能已被 broker 持久化，重试可能产生重复，需要业务侧幂等。
  • ack/reject 是单向写：不等待 broker 确认；连接断开时抛 ConnectionException。未 ack 的消息在连接断开后会由 broker 重新投递。
  • Ping 只在读取时回应：receive() 或等待发布应答期间收到 Ping 会立即回 Pong；两次读取之间没有后台心跳线程。长时间不读取时 broker 可能关闭连接。
  • topic 自动创建依赖 broker 配置：broker 关闭 auto-topic-creation 且 topic 不存在时，lookup/subscribe 抛 ProtocolException（如 TopicNotFound、MetadataError）。
  • 一次 receive() 只返回一条消息；批量拉取、多消费者组协调不在范围内。

P5 / Driver

RocketMQ 驱动（实验性）

纯 PHP 实现的 Apache RocketMQ 4.x remoting 协议客户端（Erikwang2013\Messaging\Driver\RocketMq），不依赖官方 SDK 或扩展。支持 4.x broker，以及开启 remoting 兼容端口的 5.x broker；不使用 gRPC。

实验性：协议覆盖发布、拉取消费、ack/requeue、固定延迟和路由查询，但不包含事务、ACL、消息轨迹、SQL92 过滤和阿里云 ONS 认证。生产使用前请自行压测。

配置

PHP
use Erikwang2013\Messaging\Manager;

$manager = new Manager([
    'default' => 'rocketmq',
    'connections' => [
        'rocketmq' => [
            'driver' => 'rocketmq',
            'nameserver' => '127.0.0.1:9876', // 必填，host:port；省略端口时用 9876
            'group' => 'messaging',           // 消费组/生产者组名，默认 messaging
            'topic' => null,                  // 默认 topic；destination 为空字符串时使用
            'timeout' => 10.0,                // 连接与单次请求读超时（秒），默认 10.0
            'heartbeat_interval' => 30.0,     // 重复发送 HEART_BEAT 的间隔（秒），默认 30，最小 1
            'consume_from' => 'last',         // last 或 first，默认 last
            'pull_batch_size' => 1,           // 单次 PULL_MESSAGE 的 maxMsgNums，默认 1
        ],
    ],
]);

$conn = $manager->connection('rocketmq');

nameserver 支持 host、host:port、[ipv6] 和 [ipv6]:port。group、topic 与 destination 必须符合 RocketMQ 名称规则（%、字母、数字、_、-，最长 127）。topic 和消费组都需要在 broker 上允许自动创建（默认开启），或提前创建。

destination 即 RocketMQ topic。

能力

能力 支持 说明
ack ✓ UPDATE_CONSUMER_OFFSET 提交 queueOffset + 1
requeue ✓ reject(true) 通过 CONSUMER_SEND_MSG_BACK 投递到 %RETRY%group，延迟 1 秒后重新消费；reject(false) 提交并丢弃
delay（发布） ✓ delayMs 映射到 broker 默认延迟级别（1s…2h）；超过 2 小时抛 InvalidArgumentException
consumer group ✓ 每个驱动实例一个消费组；HeartBeat 注册并创建 retry topic
batch publish ✗ publishBatch() 抛 UnsupportedFeatureException
ordering ✓ 同一 queue 内按 queueOffset 有序；跨 queue 不保证
headers ✓ 标量 header 转字符串；保留 key（KEYS）和延迟
requiresActiveSubscription ✗ 首次 receive() 时按需拉取，无需预订阅

ReceivedMessage::id() 是消息属性 UNIQ_KEY，发布时由驱动生成并随响应返回，因此发布与消费两侧 id 一致。key() 来自 KEYS。attempts() 为 broker 的 reconsumeTimes + 1，重试消息为 2 起。raw() 返回解析后的存储消息数组（topic、queueId、queueOffset、physicalOffset、reconsumeTimes、properties 等）。

协议与版本范围

remoting 帧格式：totalLen(4) + headerLen(4) + JSON header + body。totalLen 不含自身的 4 字节；headerLen 低 24 位为长度，高 8 位为序列化类型（只支持 0，即 JSON）。header 字段为 code、language（PHP）、version（407，即 4.9.7 客户端版本）、opaque、flag、remark、extFields。响应通过 flag & 1 区分，opaque 做请求关联。

请求 code 用途
SEND_MESSAGE 10 发布；extFields 含 producerGroup、topic、queueId、sysFlag、bornTimestamp、flag、properties、defaultTopic、defaultTopicQueueNums
PULL_MESSAGE 11 拉取；consumerGroup、topic、queueId、queueOffset、maxMsgNums、sysFlag（只带 SUBSCRIPTION 位）、subscription
QUERY_CONSUMER_OFFSET 14 每个队列首次拉取前查询 broker 已提交位点；未找到时按 consume_from 回退
UPDATE_CONSUMER_OFFSET 15 ack/reject 提交位点
GET_MAX_OFFSET / GET_MIN_OFFSET 30 / 31 首次拉取时按 consume_from 确定起始位点
HEART_BEAT 34 注册消费组与订阅、触发 %RETRY%group topic 创建；按间隔重复发送
CONSUMER_SEND_MSG_BACK 36 requeue；携带物理 offset、group、delayLevel、originMsgId、originTopic
GET_ROUTEINFO_BY_TOPIC 105 从 nameserver 查询 TopicRouteData

响应码处理：SUCCESS(0) 正常；PULL_NOT_FOUND(19)、PULL_RETRY_IMMEDIATELY(20) 视为本次无消息；PULL_OFFSET_MOVED(21) 采用响应的 nextBeginOffset；NO_PERMISSION(16) 抛 AuthenticationException；其余非零码抛 RequestException，statusCode() 为 broker 响应码，responseBody() 为 remark。

发布流程：先查 topic 路由；topic 尚不存在时回退到 TBW102 默认 topic 的路由发送，由 broker 自动建 topic，随后刷新路由。带 key 时按 crc32(key) 选择写队列，否则轮询。成功响应的 msgId、queueId、queueOffset 放在 PublishResult::$raw。

消费流程：短轮询（每轮间隔 20–50ms），按 queue 轮转 PULL_MESSAGE；解析 broker 返回的连续存储消息记录（magic 0xDAA320A7 / 0xDAA320AB，含 IPv6 host 标志位）。不发送 long-polling 的 suspend 标志。每个队列第一次拉取前先用 QUERY_CONSUMER_OFFSET 查询 broker 已提交位点，没有已提交位点时才按 consume_from 取 min/max；retry 队列在无已提交位点时始终从最小位点开始，避免漏掉刚 requeue 的消息。同时消费 %RETRY%group，按消息属性 RETRY_TOPIC 归还原 destination。压缩消息（compressed flag）抛 UnsupportedFeatureException。

语义

  • 发布：同步发送，一次一条。失败直接抛异常，不自动重试；重试可能产生重复消息。
  • 消费位点：每个队列首次拉取前调用 QUERY_CONSUMER_OFFSET；broker 返回已提交位点（>= 0）时从该位点继续，否则按 consume_from 取 min/max（retry 队列取 min）。ack/reject 时通过 UPDATE_CONSUMER_OFFSET 提交。进程重启后会从 broker 已提交位点恢复，崩溃前已拉取但未 ack 的消息会重新投递。
  • 心跳：按 heartbeat_interval（默认 30 秒，最小 1 秒）对每个 broker 地址重复发送 HEART_BEAT，subscriptionDataSet 携带当前 destination 的订阅（subString 为 *），避免空闲消费者被 broker 移除；连接断开后下次拉取会重新注册。
  • ack / reject：ack() 与 reject(false) 提交 queueOffset + 1；提交是单调的，旧位点不会覆盖新位点。reject(true) 先 send-back，再提交原队列位点；send-back 失败会回退本地拉取位点并抛出异常，消息不会被静默丢弃。
  • 重试：broker 固定把 send-back 消息投递到 %RETRY%group，驱动自动消费并还原 topic，attempts() 递增。重试延迟固定为 broker 延迟级别 1（1 秒），不读取消息头里的 DELAY 级别。
  • 延迟发布：delayMs 选择不小于请求值的最小 broker 延迟级别：1s、5s、10s、30s、1m、2m…10m、20m、30m、1h、2h 共 18 级。请求超过 2 小时会抛异常。
  • headers：Message::$headers 的标量值按字符串写入消息属性；接收时除 RocketMQ 系统属性外的属性作为 headers 返回（值均为字符串）。KEYS、UNIQ_KEY、WAIT、DELAY、RETRY_TOPIC 等系统属性名不能作为自定义 header，否则抛 InvalidArgumentException。
  • 并发：同步实现，每个驱动实例只应有一个消费循环；PHP 同步模型下不是线程安全的。

限制

  • 实验性协议实现；未在全部 4.x/5.x 版本矩阵上验证，5.x 需要 broker 开启 remoting 端口。
  • 不支持事务消息、事务回查、消息轨迹、ACL/鉴权、阿里云 ONS/SASL 认证。
  • 不支持 SQL92 或 TAG 过滤：PULL_MESSAGE 使用空订阅（等同 *），所有消息都会返回。
  • 不支持批量发布、批量拉取之外的高级流控/消费重平衡；pull_batch_size > 1 时多余消息缓存在进程内。
  • 不支持压缩消息体；接收压缩消息会抛 UnsupportedFeatureException。
  • 不支持 broker 端 long polling（suspend），空闲时按 20–50ms 间隔短轮询，队列多时请求量较大。
  • 心跳只在拉取前按间隔发送；驱动实例完全没有 receive() 调用时不会在后台发送心跳。
  • 只有 master broker 参与读写；不支持从 slave 拉取、broker 切换时的自动重选和 suggestWhichBrokerId 重定向。
  • 延迟只支持 broker 默认的 18 个级别，不支持自定义 messageDelayLevel 的时间表。
  • 不检查 defaultTopicQueueNums 与 broker 配置的差异；依赖 autoCreateTopicEnable=true 或预建 topic。
  • 生产端不发送 HeartBeat、不注册 producer group；依赖 broker 的宽松校验。
